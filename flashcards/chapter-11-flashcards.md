## Chapter 11: Batch, Streaming, and Real-Time Model Serving — Flashcards

| # | Front (Question) | Back (Answer) |
|---|-----------------|---------------|
| 1 | Function to create a Spark UDF from an MLflow model for batch inference | mlflow.pyfunc.spark_udf(spark, model_uri) — returns a Spark UDF applied via withColumn/select. Exam tip: this is the go-to for scaled batch scoring on large DataFrames. |
| 2 | URI format for a Unity Catalog registered model | models:/<catalog>.<schema>.<model_name>/<version_or_alias> e.g. models:/main.default.churn_model/3 or models:/main.default.churn_model@champion. Exam tip: UC uses aliases (like @champion) instead of the old Staging/Production stages. |
| 3 | Best tool for low-latency, single-record, real-time predictions | Databricks Model Serving endpoint (REST API). Exam tip: purpose-built for interactive apps needing millisecond-scale responses. |
| 4 | Best tool for scoring millions of rows already at rest in a Delta table with no latency requirement | mlflow.pyfunc.spark_udf for distributed batch inference. Exam tip: leverages cluster parallelism; far cheaper than per-row REST calls. |
| 5 | Best tool for scoring records as they continuously arrive (new files, streaming source) | Structured Streaming pipeline calling the same spark_udf inside a readStream/writeStream job. Exam tip: pairs well with Auto Loader for new-file ingestion. |
| 6 | Does mlflow.pyfunc.spark_udf work on both static and streaming DataFrames? | Yes — it returns a standard Spark UDF usable identically with df.withColumn on batch or streaming DataFrames. Exam tip: there is no separate 'streaming-only' inference API. |
| 7 | Model Serving endpoint scaling behavior | Endpoints autoscale compute based on request volume and can scale down to zero during idle periods to reduce cost. Exam tip: scale-to-zero introduces a cold-start delay on the next request after idling. |
| 8 | Command to load a UC model for plain single-node Python inference (not Spark) | mlflow.pyfunc.load_model(model_uri) where model_uri='models:/catalog.schema.model/version'. Exam tip: use load_model for non-distributed inference; spark_udf for distributed batch scoring. |
| 9 | Common wrong exam answer: scoring millions of rows by calling a Model Serving REST endpoint per row | Wrong — per-row REST calls create huge network overhead and don't scale. Correct approach for large batch jobs: mlflow.pyfunc.spark_udf. |
| 10 | Structured Streaming inference pipeline pattern (conceptual outline) | df = spark.readStream.format('delta'\|'kafka')...load(); predict_udf = mlflow.pyfunc.spark_udf(spark, model_uri); scored = df.withColumn('prediction', predict_udf(*cols)); scored.writeStream.format('delta').start(path). Exam tip: same UDF logic as batch, just applied to a streaming source/sink. |
| 11 | Key settings when creating a Model Serving endpoint | Model name + version/alias (from the model registry), compute/workload size, and scale-to-zero toggle. Exam tip: workload size (and CPU vs GPU) should match the model's inference resource needs. |
| 12 | Core latency vs throughput tradeoff: Model Serving vs spark_udf batch | Model Serving = low latency per single request, lower per-node throughput — good for interactive/real-time apps. spark_udf batch = high aggregate throughput via cluster parallelism, higher end-to-end latency — good for large offline scoring. Exam tip: match the scenario's latency requirement to the correct tool. |
